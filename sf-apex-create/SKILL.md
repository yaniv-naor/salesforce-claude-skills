# SF Apex Create

Creates production-grade Apex classes with proper structure, test coverage, and attribution comments. **Works with any Salesforce project** regardless of naming conventions or structure.

## When to Use

- Creating any new Apex class (Handler, Controller, Batch, Queueable, Service, Selector, Domain, REST, Utility, Invocable)
- Modifying existing Apex classes
- Adding new functionality to existing classes
- Refactoring Apex code

## Instructions

### Step 1: Detect Project Prefix

Use `sf-prefix-detect` skill to determine the project prefix.

**Quick fallback (if skill unavailable):**
1. Get working directory name
2. Apply transformation:
   - `Crm[Name]` → `[NAME]_`
   - `[Name]` → `[NAME]_`
3. Validate: 2-10 uppercase characters + underscore

### Step 2: Gather Class Information

Ask user for (or infer from request):

**Required:**
- **Class name** (without prefix — will be added automatically)
- **Class type**: Handler, Controller, Batch, Queueable, Service, Selector, Domain, REST, Utility, Invocable, or Other
- **Purpose/Description**: What does this class do?

**Optional (smart defaults):**
- Target object (for Handlers, Services, Selectors, Domains)
- Sharing mode: `with sharing` (default), `without sharing`, `inherited sharing`
- API version: Read from `sfdx-project.json` or default to `66.0`

**Auto-detected:**
- Current date: `[Month, Year]` (e.g., "April, 2026")
- ISO date: `[YYYY-MM-DD]` for attribution

### Step 3: Choose Class Pattern

Based on class type, select the appropriate template and structure:

| Class Type | Purpose | Key Traits |
|------------|---------|------------|
| **Service** | Business logic orchestration | `with sharing`, delegates to Selectors/Domains, no inline SOQL |
| **Selector** | SOQL queries | `inherited sharing`, returns `List<SObject>` or `Map<Id, SObject>` |
| **Domain** | Business rules, validation | `with sharing`, operates on in-memory collections, no SOQL/DML |
| **Handler** | Trigger logic | `with sharing`, methods per trigger context (beforeInsert, afterUpdate, etc.) |
| **Controller** | LWC/Aura backend | `with sharing`, `@AuraEnabled` methods, `AuraHandledException` for errors |
| **Batch** | Large dataset processing | `with sharing`, implements `Database.Batchable<SObject>` |
| **Queueable** | Async processing | `with sharing`, implements `Queueable`, optionally `Database.AllowsCallouts` |
| **Schedulable** | Scheduled jobs | `with sharing`, delegates to Batch or Queueable |
| **Invocable** | Flow actions | `with sharing`, `@InvocableMethod`, Request/Response inner classes |
| **REST** | REST API endpoints | `global with sharing`, `@RestResource`, versioned URLs |
| **Utility** | Helper methods | No sharing keyword, all `public static`, pure functions |

## Critical Rules

### Hard-Stop Constraints (Must Enforce)

Never generate code that violates these rules:

| Rule | Why |
|------|-----|
| SOQL outside loops | Avoid 100-query governor limit |
| DML outside loops | Avoid 150-DML governor limit |
| Explicit sharing keyword | Prevent unintended data exposure |
| No hardcoded IDs | Ensure portability across orgs |
| Handle all exceptions | Prevent silent failures |
| Bind variables in dynamic SOQL | Prevent SOQL injection |
| Use Apex collections (`List`/`Map`/`Set`) | Java types don't compile |
| Avoid `System.debug()` in production | Consumes CPU even when logging disabled |
| Never use `@future` | Use Queueable instead (chainable, accepts objects) |

### Bulkification & Performance

- All public APIs accept and process collections
- Use `Map<Id, SObject>` for efficient lookups
- Use `Set<Id>` for deduplication and membership checks
- Only DML records that actually changed
- Use relationship subqueries when fetching parent + children
- Apply `LIMIT` clauses to bound result sets

### Security

- Default to `with sharing` (document exceptions)
- Use `WITH USER_MODE` in SOQL
- Use `AccessLevel.USER_MODE` in DML
- Validate dynamic SOQL via allowlist or `Schema.describe`
- Use Named Credentials for external credentials
- Throw `AuraHandledException` in `@AuraEnabled` methods
- Never expose PII in logs or error messages

### Error Handling

- Catch specific exceptions before generic `Exception`
- Preserve exception cause chains: `new CustomException('msg', cause)`
- Use `try/catch` only around code that can throw
- Return user-friendly error messages
- Log errors for debugging

### Null Safety

- Guard against null/empty inputs at method entry
- Return empty collections instead of `null`
- Use safe navigation (`?.`) for chained property access
- Use null coalescing (`??`) for default values

### Naming Conventions

- Classes: `PascalCase`
- Methods: `camelCase`, start with verb (`get`, `create`, `validate`, `is`, `has`)
- Variables: `camelCase`, descriptive nouns
- Constants: `UPPER_SNAKE_CASE`
- No abbreviations — use full descriptive names

### ApexDoc

Required on:
- Class header
- Every `public` or `global` method

Format:
```apex
/**
 * Brief description
 * @param paramName Parameter description
 * @return Return value description
 */
```
