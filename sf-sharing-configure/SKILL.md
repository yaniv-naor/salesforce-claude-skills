# SF Sharing Configure

Creates production-grade Salesforce sharing rules (Ownership-based and Criteria-based) with proper structure, validation, and project prefix support. **Works with any Salesforce project** regardless of naming conventions or structure.

## When to Use

- Creating ownership-based sharing rules (share records owned by specific roles/groups)
- Creating criteria-based sharing rules (share records matching field criteria)
- Configuring guest user sharing rules
- Granting read/edit access to roles or public groups
- Troubleshooting sharing rule deployment errors
- Setting up role hierarchy access
- Configuring sharing for custom/standard objects

## Instructions

### Step 1: Detect Project Prefix

Use `sf-prefix-detect` skill to determine the project prefix.

**Quick fallback (if skill unavailable):**
1. Get working directory name
2. Apply transformation:
   - `Crm[Name]` → `[NAME]_`
   - `[Name]` → `[NAME]_`
3. Validate: 2-10 uppercase characters + underscore

**Note:** Prefix is used to identify custom objects and to name sharing rules.

### Step 2: Verify Object Exists and Supports Sharing

**CRITICAL:** Only create sharing rules for objects that support sharing.

**Check object metadata:**
1. Read object file: `force-app/main/default/objects/[ObjectName]/[ObjectName].object-meta.xml`
2. Verify sharing model:
   - ✅ `ReadWrite` - Supports sharing rules
   - ✅ `Private` - Supports sharing rules
   - ✅ `Public Read Only` - Supports sharing rules
   - ❌ `ControlledByParent` - NO sharing rules (inherits from parent)
   - ❌ `Public Read/Write` - No sharing rules needed (everyone has access)

**Objects that DON'T support sharing rules:**
- Child objects with Master-Detail relationships (`ControlledByParent` sharing model)
- Junction objects
- Objects with Public Read/Write sharing model

**If object doesn't exist:**
1. Ask user to create object first using `sf-object-create` skill
2. Cannot create sharing rules for non-existent objects

### Step 3: Gather Sharing Rule Information

Ask user for (or infer from request):

**Required:**
- **Object name** (e.g., `Document__c`, `EnforcementCase__c`)
- **Rule type:**
  - Ownership-based: Share records owned by specific roles/groups
  - Criteria-based: Share records matching field criteria
  - Guest user: Share to guest users (for community/site access)
- **Access level:** Read or Edit
- **Shared to:** Role, group, or role and subordinates receiving access

**For Ownership-based rules (additional):**
- **Shared from:** Role or group that currently owns the records

**For Criteria-based rules (additional):**
- **Field criteria:** Field name, operation, value
- **Multiple criteria:** AND/OR logic

**For Account/Contact (additional):**
- **Related object access:** Case, Opportunity, Contact access levels (Account only)

**Auto-detected:**
- API version: Read from `sfdx-project.json` or default to `60.0`
- Rule full name: `[PREFIX]_[RuleName]` (apply prefix convention)

### Step 4: Create Base Sharing Rules Structure

Generate the base XML structure:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<SharingRules xmlns="http://soap.sforce.com/2006/04/metadata">
    <!-- Generated by Claude Code on [YYYY-MM-DD] -->
    
    <!-- Sharing rules go here -->
</SharingRules>
```

**File naming:**
- **Standard objects:** `ObjectName.sharingRules-meta.xml` (e.g., `Account.sharingRules-meta.xml`)
- **Custom objects:** `[PREFIX]_ObjectName__c.sharingRules-meta.xml` (e.g., `ABC_Document__c.sharingRules-meta.xml`)

**File location:**
```
force-app/main/default/sharingRules/
└── [ObjectName].sharingRules-meta.xml
```

### Step 5: Add Ownership-Based Sharing Rule

Use when sharing records based on who owns them.

```xml
<sharingOwnerRules>
    <fullName>RuleName</fullName>
    <accessLevel>Read</accessLevel>
    <label>Display Name for Rule</label>
    <sharedTo>
        <roleOrGroup>recipientRoleOrGroup</roleOrGroup>
    </sharedTo>
    <sharedFrom>
        <roleOrGroup>ownerRoleOrGroup</roleOrGroup>
    </sharedFrom>
</sharingOwnerRules>
```

**Key fields:**
- `<fullName>`: Rule API name (apply prefix: `[PREFIX]_RuleName`)
- `<accessLevel>`: `Read` or `Edit`
- `<label>`: Human-readable rule name
- `<sharedTo>`: Who gets access (recipient)
- `<sharedFrom>`: Who currently owns the records (source)

**sharedTo/sharedFrom options:**
- `<role>RoleDeveloperName</role>` - Specific role only
- `<roleAndSubordinates>RoleDeveloperName</roleAndSubordinates>` - Role and subordinates
- `<group>GroupDeveloperName</group>` - Public group

**Example:**
```xml
<sharingOwnerRules>
    <fullName>ABC_ShareToManagers</fullName>
    <accessLevel>Read</accessLevel>
    <label>Share to Managers</label>
    <sharedTo>
        <roleAndSubordinates>Manager</roleAndSubordinates>
    </sharedTo>
    <sharedFrom>
        <group>ABC_AllUsers</group>
    </sharedFrom>
</sharingOwnerRules>
```

**Naming convention:**
- Apply project prefix to rule name: `[PREFIX]_RuleName`
- Use descriptive names: `[PREFIX]_ShareToManagers`, `[PREFIX]_RegionalAccess`
- Labels can be more readable: "Share to Managers", "Regional Access"

### Step 6: Add Criteria-Based Sharing Rule

Use when sharing records based on field values.

```xml
<sharingCriteriaRules>
    <fullName>RuleName</fullName>
    <accessLevel>Read</accessLevel>
    <label>Display Name for Rule</label>
    <sharedTo>
        <roleOrGroup>recipientRoleOrGroup</roleOrGroup>
    </sharedTo>
    <criteriaItems>
        <field>FieldName</field>
        <operation>equals</operation>
        <value>Value</value>
    </criteriaItems>
    <includeRecordsOwnedByAll>true</includeRecordsOwnedByAll>
</sharingCriteriaRules>
```

**Key fields:**
- `<fullName>`: Rule API name (apply prefix: `[PREFIX]_RuleName`)
- `<accessLevel>`: `Read` or `Edit`
- `<label>`: Human-readable rule name
- `<sharedTo>`: Who gets access (role/group)
- `<criteriaItems>`: Field criteria (can have multiple)
- `<includeRecordsOwnedByAll>`: Share records regardless of owner (usually `true`)

**Criteria operations:**
- `equals` - Field equals value
- `notEqual` - Field not equal to value
- `lessThan` - Field less than value
- `greaterThan` - Field greater than value
- `lessOrEqual` - Field less than or equal to value
- `greaterOrEqual` - Field greater than or equal to value
- `contains` - Field contains value (text)
- `notContain` - Field does not contain value (text)
- `startsWith` - Field starts with value (text)

**Multiple criteria:**
```xml
<sharingCriteriaRules>
    <fullName>ABC_RegionalAccessRule</fullName>
    <accessLevel>Edit</accessLevel>
    <label>Regional Access Rule</label>
    <sharedTo>
        <role>RegionalManager</role>
    </sharedTo>
    <booleanFilter>1 AND 2</booleanFilter>
    <criteriaItems>
        <field>Status__c</field>
        <operation>equals</operation>
        <value>Active</value>
    </criteriaItems>
    <criteriaItems>
        <field>Region__c</field>
        <operation>equals</operation>
        <value>North</value>
    </criteriaItems>
    <includeRecordsOwnedByAll>true</includeRecordsOwnedByAll>
</sharingCriteriaRules>
```

**Boolean filter:**
- Default: All criteria combined with AND
- Custom: Use `<booleanFilter>` for complex logic
- Examples: `1 AND 2`, `1 OR 2`, `(1 OR 2) AND 3`

**Field naming:**
- **Custom fields:** Include `__c` suffix (e.g., `Status__c`, `Region__c`)
- **Standard fields:** Use exact API name (e.g., `RecordTypeId`, `Name`)
- **Relationship fields:** Use `__r` notation (e.g., `Account__r.Type`)

### Step 7: Add Guest User Sharing Rule (Optional)

Use for sharing to guest users in communities/sites.

```xml
<sharingGuestRules>
    <fullName>RuleName</fullName>
    <accessLevel>Read</accessLevel>
    <label>Display Name for Rule</label>
    <sharedTo>
        <guestUser>SiteName</guestUser>
    </sharedTo>
    <criteriaItems>
        <field>IsPublic__c</field>
        <operation>equals</operation>
        <value>True</value>
    </criteriaItems>
    <includeHVUOwnedRecords>false</includeHVUOwnedRecords>
</sharingGuestRules>
```

**Key fields:**
- `<guestUser>`: Site/community name
- `<includeHVUOwnedRecords>`: Include high volume user owned records (usually `false`)

**CRITICAL:** Guest user rules only apply to communities/sites with guest access enabled.

### Step 8: Add Account/Contact Specific Settings

For Account and Contact objects, specify related object access levels.

**Account object only:**
```xml
<sharingCriteriaRules>
    <fullName>ABC_AccountSharingRule</fullName>
    <accessLevel>Edit</accessLevel>
    <accountSettings>
        <caseAccessLevel>None</caseAccessLevel>
        <contactAccessLevel>None</contactAccessLevel>
        <opportunityAccessLevel>None</opportunityAccessLevel>
    </accountSettings>
    <label>Account Sharing Rule</label>
    <sharedTo>
        <group>ABC_AllUsers</group>
    </sharedTo>
    <criteriaItems>
        <field>RecordTypeId</field>
        <operation>equals</operation>
        <value>Structure</value>
    </criteriaItems>
    <includeRecordsOwnedByAll>true</includeRecordsOwnedByAll>
</sharingCriteriaRules>
```

**Access levels for related objects:**
- `None` - No access to related records
- `Read` - Read access to related records
- `Edit` - Edit access to related records

**Contact object only:**
```xml
<sharingCriteriaRules>
    <fullName>ABC_ContactSharingRule</fullName>
    <accessLevel>Edit</accessLevel>
    <contactSettings>
        <caseAccessLevel>None</caseAccessLevel>
        <opportunityAccessLevel>None</opportunityAccessLevel>
    </contactSettings>
    <!-- ... -->
</sharingCriteriaRules>
```

**IMPORTANT:** Only include these settings for Account/Contact objects. Other objects don't have related object access.

### Step 9: Validate Sharing Rules

Run validation checks before saving:

**Required fields:**
- [ ] `<fullName>` is set with prefix
- [ ] `<accessLevel>` is `Read` or `Edit`
- [ ] `<label>` is set
- [ ] `<sharedTo>` has valid role/group/roleAndSubordinates
- [ ] For ownership rules: `<sharedFrom>` is set
- [ ] For criteria rules: At least one `<criteriaItems>` exists
- [ ] For criteria rules: `<includeRecordsOwnedByAll>` is set

**Object validation:**
- [ ] Object exists in metadata
- [ ] Object sharing model supports sharing rules (not `ControlledByParent`)
- [ ] Object is not Public Read/Write (sharing rules not needed)

**Naming validation:**
- [ ] Rule name includes project prefix: `[PREFIX]_RuleName`
- [ ] Rule name is unique within the sharing rules file
- [ ] File name matches object API name

**Criteria validation:**
- [ ] Field exists on object
- [ ] Custom fields have `__c` suffix
- [ ] Operation is valid for field type
- [ ] Boolean filter references existing criteria (if used)

**Common errors to prevent:**
- Object with `ControlledByParent` → NO sharing rules allowed
- Missing prefix on rule name → Inconsistent naming
- Invalid role/group name → DEPLOYMENT FAILURE
- Non-existent field in criteria → DEPLOYMENT FAILURE
- Boolean filter referencing non-existent criteria → DEPLOYMENT FAILURE

### Step 10: Handle Multiple Sharing Rules

Multiple rules can exist in the same file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<SharingRules xmlns="http://soap.sforce.com/2006/04/metadata">
    <!-- Ownership-based rules -->
    <sharingOwnerRules>
        <!-- Rule 1 -->
    </sharingOwnerRules>
    <sharingOwnerRules>
        <!-- Rule 2 -->
    </sharingOwnerRules>
    
    <!-- Criteria-based rules -->
    <sharingCriteriaRules>
        <!-- Rule 3 -->
    </sharingCriteriaRules>
    <sharingCriteriaRules>
        <!-- Rule 4 -->
    </sharingCriteriaRules>
    
    <!-- Guest user rules -->
    <sharingGuestRules>
        <!-- Rule 5 -->
    </sharingGuestRules>
</SharingRules>
```

**When adding to existing file:**
1. Read existing sharing rules file
2. Identify existing rules
3. Add new rule in appropriate section (owner/criteria/guest)
4. Ensure unique rule names
5. Maintain XML structure

## Sharing Rule Patterns

### Pattern 1: Simple Ownership Rule

**Scenario:** Share all records owned by Sales Reps to Sales Managers

```xml
<?xml version="1.0" encoding="UTF-8"?>
<SharingRules xmlns="http://soap.sforce.com/2006/04/metadata">
    <!-- Generated by Claude Code on 2026-05-05 -->
    
    <sharingOwnerRules>
        <fullName>ABC_ShareToManagers</fullName>
        <accessLevel>Read</accessLevel>
        <label>Share to Sales Managers</label>
        <sharedTo>
            <role>SalesManager</role>
        </sharedTo>
        <sharedFrom>
            <role>SalesRep</role>
        </sharedFrom>
    </sharingOwnerRules>
</SharingRules>
```

**File name:** `ABC_Opportunity__c.sharingRules-meta.xml`

## Critical Rules & Constraints

### Object Sharing Model Requirements

**MUST ENFORCE:**

| Sharing Model | Supports Sharing Rules? | Why |
|---------------|------------------------|-----|
| `Private` | ✅ YES | Users need explicit access via sharing |
| `Public Read Only` | ✅ YES | Can grant write access via sharing |
| `ReadWrite` | ✅ YES | Can grant additional access via sharing |
| `ControlledByParent` | ❌ NO | Inherits from parent (Master-Detail) |
| `Public Read/Write` | ⚠️ NO | Everyone has full access (no need for rules) |

**❌ Common Error:**
```
Cannot create sharing rules for object with ControlledByParent sharing model
```

**✅ Solution:** Don't create sharing rules for child objects with Master-Detail relationships. They inherit sharing from parent object.

### Access Level Rules

**Valid access levels:**
- `Read` - View record and fields
- `Edit` - View and edit record

**CRITICAL:** Cannot use sharing rules to restrict access below org-wide defaults. Sharing rules are **additive only**.

**Example:**
- Org-wide default: Public Read Only
- Sharing rule can grant: Edit (adds write access)
- Sharing rule CANNOT restrict to: Private (cannot reduce from Read)

### Role and Group Naming

**Valid sharedTo/sharedFrom values:**

| Type | Tag | Format | Example |
|------|-----|--------|---------|
| Role | `<role>` | Role Developer Name | `SalesManager` |
| Role + Subordinates | `<roleAndSubordinates>` | Role Developer Name | `RegionalManager` |
| Public Group | `<group>` | Group Developer Name | `ABC_AllUsers` |

**IMPORTANT:** Use Developer Names (API names), not Labels.

**How to find role/group names:**
- **Roles:** Setup → Roles → Click role → Check "API Name" or "Developer Name"
- **Groups:** Setup → Public Groups → Click group → Check "API Name"

**Common error:**
```
Invalid role or group name: SalesManager [Label]
Should be: Sales_Manager [API Name]
```

**Prefix convention for groups:**
- Apply project prefix to public group names you create: `[PREFIX]_GroupName`
- Standard Salesforce roles don't need prefix
- Check existing groups for naming pattern

### Field Criteria Rules

**Valid field types for criteria:**
- Text fields (all operations)
- Picklist fields (equals, notEqual)
- Number fields (all numeric operations)
- Date/DateTime fields (all date operations)
- Checkbox fields (equals true/false)
- Lookup/Master-Detail (equals record ID - rare)

**Invalid field types:**
- Long text area (too large)
- Rich text area (too complex)
- Multi-select picklist (complex comparison)

**Field naming in criteria:**
- **Custom fields:** Include `__c` suffix
- **Standard fields:** Use exact API name
- **Relationship fields:** Use `__r.FieldName` notation (if supported)

### Boolean Filter Rules

**Default behavior:** All criteria combined with AND

**Custom boolean filter:**
- Reference criteria by number (1, 2, 3...)
- Use AND, OR, NOT operators
- Use parentheses for grouping
- Examples:
  - `1 AND 2` - Both conditions must be true
  - `1 OR 2` - Either condition can be true
  - `(1 OR 2) AND 3` - Either 1 or 2, plus 3
  - `1 AND (2 OR 3)` - 1 plus either 2 or 3

**Validation:**
- Must reference existing criteria numbers
- Cannot reference non-existent criteria
- Must use valid operators (AND, OR, NOT)

**Example:**
```xml
<booleanFilter>1 AND (2 OR 3)</booleanFilter>
<criteriaItems>
    <field>Status__c</field>
    <operation>equals</operation>
    <value>Active</value>
</criteriaItems>
<criteriaItems>
    <field>Priority__c</field>
    <operation>equals</operation>
    <value>High</value>
</criteriaItems>
<criteriaItems>
    <field>Type__c</field>
    <operation>equals</operation>
    <value>Urgent</value>
</criteriaItems>
```

**Interpretation:** Status is Active AND (Priority is High OR Type is Urgent)

### Sharing Rule Limits

**Per object:**
- Maximum 300 sharing rules per object (combined ownership + criteria + guest)
- Maximum 50 criteria per rule

**Performance:**
- More sharing rules = slower sharing calculations
- Complex criteria = longer calculation time
- Consider consolidating rules when possible

**Best practices:**
- Use role hierarchy when possible (automatic)
- Combine similar rules with OR boolean filter
- Use public groups to simplify sharing to multiple roles
- Test performance with large data volumes

## Verification Checklist

Before generating sharing rule XML, verify:

### Object Validation
- [ ] Object exists in metadata
- [ ] Object sharing model supports sharing rules (not `ControlledByParent`)

## Common Deployment Failures

### Error 1: Object doesn't support sharing rules

**Error message:**
```
Cannot create sharing rules for object with sharing model ControlledByParent
```

**Cause:** Object is a child in Master-Detail relationship

**Solution:**
1. Check object's `<sharingModel>` in object metadata
2. If `ControlledByParent`, cannot create sharing rules
3. Instead, create sharing rules on parent object
4. Child records inherit parent's sharing

**Example:**
- ❌ Cannot create sharing rules on `Invoice_Line_Item__c` (child)
- ✅ Create sharing rules on `Invoice__c` (parent)
- Line items automatically inherit invoice sharing

**Cause:**

### Error 4: Invalid boolean filter

**Error message:**
```
Invalid boolean filter: References non-existent criterion 4
```

**Cause:**
- Boolean filter references criterion number that doesn't exist
- Criteria numbered 1, 2, 3 but filter references 4

**Solution:**
1. Count criteria items (starts at 1)
2. Ensure boolean filter only references existing criteria
3. Check for typos in boolean filter expression

**Example:**
```xml
<!-- WRONG: Only 2 criteria but filter references 3 -->
<booleanFilter>1 AND 3</booleanFilter>
<criteriaItems><!-- Criterion 1 --></criteriaItems>
<criteriaItems><!-- Criterion 2 --></criteriaItems>

<!-- CORRECT -->
<booleanFilter>1 AND 2</booleanFilter>
<criteriaItems><!-- Criterion 1 --></criteriaItems>
<criteriaItems><!-- Criterion 2 --></criteriaItems>
```

### Error 5: Sharing rule already exists

**Error message:**

**Cause:**

   - Use different rule name
   - Update existing rule instead of adding new
   - Remove old rule before adding new

### Issue: Don't know if object supports sharing rules

**Solution:**
1. Read object metadata file

4. If `ControlledByParent`, explain cannot create sharing rules

### Issue: Role/group name unclear

**Solution:**
1. Ask user for exact Developer Name
2. Check existing sharing rules in repo for naming patterns
3. Common pattern: Apply prefix to custom groups (e.g., `ABC_AllUsers`)
4. Standard roles typically don't have prefix (e.g., `SalesManager`)

### Issue: Multiple criteria with complex logic

**Solution:**
1. Number each criterion (1, 2, 3, ...)
2. Ask user for boolean logic: "Should all conditions be true (AND) or any condition (OR)?"
3. Create `<booleanFilter>` with appropriate expression
4. Example: "Status is Active AND (Priority is High OR Type is Urgent)" → `1 AND (2 OR 3)`

### Issue: Sharing rule file already exists

**Solution:**
1. Read existing file
2. Ask user:
   - Add to existing sharing rules
   - Replace entire file
   - Create separate rule (add to existing)
3. Most common: Add new rule to existing file

### Issue: Need to share to multiple roles/groups

**Solution:**
1. Option A: Create multiple sharing rules (one per role/group)
2. Option B: Suggest creating public group that includes multiple roles
3. Option B is cleaner: One sharing rule shared to group, group contains all roles

## Reference

**File structure:**
```
force-app/main/default/sharingRules/
├── Account.sharingRules-meta.xml

```

**Sharing rule types:**

| Type | Element | Use Case |
|------|---------|----------|
| Ownership-based | `<sharingOwnerRules>` | Share records owned by specific role/group |
| Criteria-based | `<sharingCriteriaRules>` | Share records matching field criteria |
| Guest user | `<sharingGuestRules>` | Share to guest users in communities |

**Access levels:**

| Level | Permission | Can... |
|-------|-----------|--------|
| `Read` | View only | See record and fields |
| `Edit` | View and edit | See and modify record |

**sharedTo/sharedFrom options:**

| Tag | Meaning | Example |
|-----|---------|---------|
| `<role>` | Specific role only | `<role>SalesManager</role>` |
| `<roleAndSubordinates>` | Role + subordinates | `<roleAndSubordinates>RegionalManager</roleAndSubordinates>` |
| `<group>` | Public group | `<group>ABC_AllUsers</group>` |

**Criteria operations:**

| Operation | Meaning | Valid For |
|-----------|---------|-----------|
| `equals` | Field equals value | All types |
| `notEqual` | Field not equal | All types |
| `lessThan` | Field < value | Number, Date |
| `greaterThan` | Field > value | Number, Date |
| `lessOrEqual` | Field <= value | Number, Date |
| `greaterOrEqual` | Field >= value | Number, Date |
| `contains` | Contains text | Text |
| `notContain` | Doesn't contain | Text |
| `startsWith` | Starts with | Text |

**Naming patterns:**

| Component | Pattern | Example |
|-----------|---------|---------|
| Ownership rule name | `[PREFIX]_RuleName` | `ABC_ShareToManagers` |
| Criteria rule name | `[PREFIX]_RuleName` | `ABC_ActiveDocuments` |
| Guest rule name | `[PREFIX]_RuleName` | `ABC_PublicAccess` |
| File name (standard) | `ObjectName.sharingRules-meta.xml` | `Account.sharingRules-meta.xml` |
| File name (custom) | `[PREFIX]_Object__c.sharingRules-meta.xml` | `ABC_Document__c.sharingRules-meta.xml` |

**Account/Contact specific settings:**

| Object | Setting | Options |
|--------|---------|---------|
| Account | `caseAccessLevel` | None, Read, Edit |
| Account | `contactAccessLevel` | None, Read, Edit |
| Account | `opportunityAccessLevel` | None, Read, Edit |
| Contact | `caseAccessLevel` | None, Read, Edit |
| Contact | `opportunityAccessLevel` | None, Read, Edit |

**Key constraints:**
- Maximum 300 sharing rules per object
- Maximum 50 criteria per rule
- Sharing rules are additive only (cannot restrict)
- Objects with `ControlledByParent` cannot have sharing rules
- Role hierarchy provides automatic upward sharing
- Guest user rules require community/site with guest access
